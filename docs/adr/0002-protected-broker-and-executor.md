# Protected broker and separate executor

Phone signatures enforce consent only if an agent cannot replace the verifier or its trusted keys. Protected mode therefore runs the broker under a dedicated non-login `_xlatch` account, with administrator-owned executable, configuration, parent directories and OS service definitions. Approval state is service-owned and private. Startup rejects incorrect ownership, writable paths, unsafe macOS ACLs, and an executor sharing the broker's identity.

The broker never executes capability bindings in protected mode. A separate ordinary-user process leases approved jobs over a Unix socket. Socket access is checked against the configured executor UID; other peers are disconnected without stopping the daemon. That UID may register proposals, issue pending pairing tickets, inspect the registry, and execute leased work. Local approval, grants, revocation, bootstrap and invocation shortcuts are denied. Phones keep using the signed capability RPC protocol. Registration performs contract validation without reading host files; executable hashes and filesystem destinations are checked only by a trusted operator or the unprivileged executor.

A lease is random, bound to one durable job, and created in the same transaction that claims the job. The broker rechecks the active revision and grants before handing out work, checks returned output against the saved manifest, and never lets a late result revive a cancelled job. Expired or interrupted work fails instead of repeating possible side effects. Cancellation and lost broker access terminate command execution. The executor has no approval database or service credentials; it has the permissions of its ordinary OS user. It is trusted to execute work and report results, not to authorize enrollment. Files and credentials already accessible to that user are outside this protection.

Migration cannot blindly trust a user-writable database or reuse a TLS private key that remains readable by agents. The installer requires a fingerprint calculated on the existing approver phone from its locally held request and approval keys, device ID and remembered server identity. The imported state must contain exactly that one approver. Other devices and old tickets are invalidated, and the new broker generates a fresh TLS key inside its private directory. The approver explicitly scans the new certificate identity after installation, retaining its existing keys; other clients pair again. The original user data is preserved for manual rollback, not consulted by the protected broker.

macOS uses two system LaunchDaemons with distinct UserName values. Linux uses two systemd services; the broker receives a narrow writable filesystem, while the executor retains ordinary-user filesystem access for configured save destinations. Installation is explicit and supports a complete JSON dry-run. Windows service identities remain separate follow-up work.

This first protected mode supports the already approved capabilities carried through migration. Phone approval for new capability revisions, new grants, approver replacement, and recovery are subsequent protocol operations; the protected local socket does not provide temporary bypasses for them. Oqto should adapt to these permission and job contracts rather than obtain an unrestricted operator socket. MCP remains an adapter.
